# 校园社团管理与招新系统 - 系统设计说明书

## 1. 引言

### 1.1 目的
本设计说明书基于《需求规格说明书》，提供校园社团管理与招新系统的整体技术架构、模块划分、数据模型、关键流程与非功能设计，指导后续开发与运维。

### 1.2 范围
涵盖后端服务（Spring Boot）、前端（Web / 小程序拓展）、数据库设计、缓存与消息、权限与安全、部署架构、监控与扩展策略。

---

## 2. 总体架构

### 2.1 架构风格
采用分层 + 领域划分（分包而非强微服务的单体可演进）战略：
- 表现层 (API Controller)
- 应用层 (Service / Facade / Orchestrator)
- 领域层 (Domain Model + Domain Service)
- 基础设施层 (Repository, External Adapters, Cache, Messaging)

预留向 Spring Cloud / Kubernetes 微服务拆分的路径：按“用户与认证”“社团与招新”“活动与资源”“通知与消息”“统计分析”拆分。

### 2.2 技术选型
| 组件 | 技术 | 选择理由 |
|------|------|---------|
| 后端框架 | Spring Boot 3.x | 主流生态、快速开发、云原生支持 |
| 安全框架 | Spring Security + JWT | 标准化认证授权，易扩展角色模型 |
| ORM | Spring Data JPA / MyBatis Plus（二选一） | 结合团队经验与性能要求 |
| 数据库 | MySQL 8.0 | 事务一致性强，易维护 |
| 缓存 | Redis | 热点数据与分布式锁 |
| 对象存储 | MinIO / OSS | 存放文件/Logo/附件 |
| 消息队列（可选） | RabbitMQ / Kafka | 异步通知与高峰削峰 |
| 前端 | Vue3 + TypeScript | 组合式 API，提高可维护性 |
| 构建 | Maven + Docker | 规范化依赖与容器化部署 |
| CI/CD | Jenkins / GitLab CI | 自动化构建测试发布 |
| 监控 | Prometheus + Grafana | 指标采集与可视化 |
| 日志 | ELK / OpenSearch | 集中日志与检索 |

### 2.3 模块划分
1. auth-module：认证、授权、令牌刷新、权限校验。
2. user-module：用户档案、角色分配、密码重置。
3. club-module：社团信息、标签、Logo、审核状态。
4. recruitment-module：招新批次、表单字段、报名、审核流。
5. member-module：成员档案、积分、状态变更、统计聚合。
6. activity-module：活动创建、报名、签到、总结归档。
7. notice-module：公告发布、已读状态、消息推送。
8. resource-module（扩展）：场地/物资申请与审批。
9. stats-module：报表聚合、数据仓库入口（ETL）。
10. audit-module：审计日志记录与检索。

### 2.4 分层结构示意
```
Controller -> Application(Service/Fascade) -> Domain(Model/Policy) -> Repository(Adapter) -> DataSource(MySQL/Redis/OSS)
                                   ^                          |
                                   |                          +--> EventPublisher (MQ)
                                   +--> SecurityContext / ACL
```

### 2.5 权限与安全设计
- RBAC + 细粒度资源校验（方法级 + 数据行级）。
- 注解 `@PreAuthorize("hasAuthority('CLUB_EDIT')")` 结合自定义 PermissionEvaluator。
- 数据行级：仅社团负责人或管理员可修改该社团资源；成员仅访问自身申请记录。
- 敏感操作写入审计日志（登录失败、角色变更、录取决策）。

### 2.6 缓存策略
- 热点：社团列表、活动详情（短 TTL 5~10 分钟）。
- 防穿透：空结果缓存与访问频次限制。使用 Redis + Lua 脚本实现原子计数限流。
- 失效策略：更新/删除后主动删除相关 key（Cache Aside）。

### 2.7 日志与监控
- 业务日志：操作类型、主体、资源、结果；JSON 结构化输出。
- 指标：报名提交速率、队列积压、活动签到延迟、错误率、P95/P99 延迟。
- 警报规则：报名失败率 >5%、登录失败暴力尝试、数据库连接池耗尽。

### 2.8 异步与事件
- 招新录取完成 → 发布 `MemberOnboardedEvent` → 异步发送通知/更新统计。
- 活动结束 → 发布 `ActivityArchivedEvent` → 异步生成报表与持久化总结。

### 2.9 事务与一致性
- 采用本地事务（单库阶段），关键组合：报名提交（报名表 + 审计日志）。
- 事件外发使用事务消息或 Outbox 表（定时扫描 + 可靠投递）避免丢失。

### 2.10 扩展规划
- 第二阶段可拆分 recruitment-module 与 activity-module 为独立服务，通过 API 或消息交互；共享统一认证与网关。

## 3. 关键流程设计

### 3.1 招新审核流程
```
学生提交报名 -> 系统校验表单 -> 入库 (PENDING) -> 干部初审 (PASS/REJECT + 评分) -> 负责人复审 -> 状态 FINAL_PASS -> 创建成员档案 -> 异步发送录取通知。
```
状态机：PENDING → FIRST_PASS / REJECT → FINAL_PASS / FINAL_REJECT
限制：复审仅在初审通过的记录上进行；录取名额控制使用 Redis 分布式计数（溢出进入候补）。

### 3.2 活动签到流程
```
活动发布 -> 生成签到二维码 (活动ID + 时间戳 + 签名) -> 成员扫码 -> 验证身份与报名状态 -> 写入签到记录 -> 超时后二维码失效 -> 结束后统计出勤率。
```
防刷：单人重复签到校验 + IP/设备指纹过滤。

### 3.3 公告发布与推送
负责人/管理员发布公告 → 入库 → 写消息队列 (notice-topic) → 推送服务消费 → 分发站内信/邮件/微信（可选）。

### 3.4 成员积分更新
事件触发：参与活动签到、被评为优秀志愿者。通过事件驱动累加积分，避免并发写冲突（使用 Redis 原子递增 + 定期落库）。

### 3.5 统计报表聚合
定时任务（Quartz / Spring Scheduling）每日夜间汇总：
- 招新转化率 = 录取人数 / 报名人数
- 活动参与率 = 实际到场 / 报名人数
- 活跃度指数 = 加权(活动数, 公告数, 成员在线数)

## 5. API 分层示例 (以招新创建为例)
Controller: 校验 DTO → 调用 ApplicationService。
ApplicationService: 业务编排（检查权限、调用领域服务、发布事件）。
DomainService: 验证名额、生成状态，返回领域对象。
Repository: 持久化 RecruitBatch / RecruitFormField。

## 6. 安全设计细节
- 登录：/api/auth/login → 返回 accessToken + refreshToken。
- Token 刷新：/api/auth/refresh → 校验 refreshToken 有效期（Redis 黑名单机制）。
- CSRF：前端仅调用后端 API，使用 Bearer Token；对修改操作加 Referer 校验（可选）。
- 数据权限：基于 clubId 和 userId 双重校验；管理员跳过 clubId 限制。

---

## 7. 性能与容量规划
- 报名高峰：预计每分钟 500 提交 → 使用异步写队列 + 限流（令牌桶）与快速失败提示。
- 活动签到：峰值并发 300 QPS → 内存缓存活动基本信息减少数据库读取。
- 统计报表：离线批处理，避免影响在线请求。

## 8. 部署架构
```
Browser / Mobile
   ↓ HTTPS
Nginx / API Gateway
   ↓
Spring Boot App (Auth / Club / Recruitment / Activity / Notice / Stats)
   ↓                ↓             ↓          ↓
MySQL  Redis   MinIO/OSS   MQ(RabbitMQ)  Prometheus
```
横向扩展：无状态服务容器 + 共享 Redis 与 DB；可使用 Consul / Nacos 做配置与注册（后期微服务化）。

## 9. 错误处理与返回规范
统一响应：
```json
{
  "code": "SUCCESS",
  "message": "操作成功",
  "data": { }
}
```
错误码分类：
- AUTH_xx，VALIDATION_xx，RESOURCE_NOT_FOUND，PERMISSION_DENIED，CONFLICT_xx，SYSTEM_ERROR。

## 10. 配置与参数化
使用 Spring Boot Config + 分环境配置（dev/test/prod）。敏感配置（DB 密码、邮件秘钥）放入 Vault / KMS。

## 11. 质量保障

- 代码扫描：SonarQube 检查重复与复杂度。
- 安全扫描：OWASP Dependency-Check。
