# 校园社团管理与招新系统 - 系统设计说明书

## 1. 引言

### 1.1 目的
本文档以当前仓库中的实际实现为准，说明校园社团管理与招新系统的真实技术架构、模块划分、关键流程与部署方式，供开发、联调和维护使用。

### 1.2 范围
本文档覆盖以下已落地内容：
- 后端：`Spring Boot 3.x` 多模块单体应用
- 前端：`Vue 3 + JavaScript + Vite`
- 智能体：独立 `FastAPI` RAG / 推荐服务
- 基础设施：`MySQL`、`Redis`、`RabbitMQ`、`Prometheus`、`Grafana`
- 文件与通知：阿里云 `OSS`、`SMTP` 邮件

不包含当前仓库中尚未实现的小程序端、统一身份认证（CAS/OAuth2）、MinIO、Kafka、ELK/OpenSearch 等内容。

## 2. 总体架构

### 2.1 架构形态
当前项目采用“多模块单体 + 独立智能体服务”的组合架构：

1. `community-gateway` 作为唯一 `Spring Boot` 启动入口。
2. 其余 Java 模块按领域拆分，通过 Maven 聚合在同一运行时内装配。
3. `agent` 目录下的 Python 服务独立运行，提供 AI 问答与推荐能力。
4. 基础设施通过 `docker-compose.yml` 统一编排。

该架构的特点是：
- 代码按领域拆分，便于维护；
- 部署仍然是一个 Java 应用，而非多个独立 Java 微服务；
- 保留了未来继续拆分的空间，但当前项目并未实现 Spring Cloud / Kubernetes 微服务体系。

### 2.2 实际技术选型
| 层次 | 技术 | 说明 |
|------|------|------|
| 后端框架 | Spring Boot 3.2.x | 系统主应用 |

| 会话承载 | HttpOnly Cookie + Redis | 前端不直接保存真实 JWT |

| 消息队列 | RabbitMQ | 通知异步投递 |
| 文件存储 | 阿里云 OSS | 图片与附件上传 |
| 邮件 | Spring Mail / SMTP | 验证码、密码重置 |
| 前端 | Vue 3 + JavaScript + Vite | 管理端 / 学生端 Web 界面 |
| UI | Element Plus | 主要组件库 |
| 图表 | ECharts | 管理端统计图表 |
| 实时能力 | WebSocket + SockJS + STOMP | 实时看板 |
| AI 服务 | FastAPI + Chroma + DeepSeek | 问答与推荐 |
| 监控 | Prometheus + Grafana | 指标采集与展示 |
| 构建部署 | Maven + Docker Compose | 本地与容器化部署 |

### 2.4 运行与部署结构

- `mysql`

- `frontend`
- `redis`

## 3. 关键设计

### 3.1 认证与安全设计
系统当前采用以下认证模式：

1. 用户通过 `/api/auth/login` 登录。
2. 后端签发 access token 与 refresh token。
3. Token 通过 `HttpOnly Cookie` 返回给浏览器。
4. refresh token 轮换信息保存在 Redis 中。
5. 前端通过 `withCredentials` 自动携带 Cookie。
6. 后端 `JwtAuthenticationFilter` 负责从 Cookie 或 `Authorization` 头中提取 token。

当前已实现的安全能力包括：
- `Spring Security` 路由保护
- `JWT` 签名校验
- Redis 记录 refresh token
- 登录失败限流
- 密码重置验证码
- 审计日志切面
- 若干管理接口的权限校验

当前未实现或未全面落地的内容：
- OAuth2 / CAS 统一认证
- 自定义 `PermissionEvaluator`
- 基于 Lua 的统一限流框架
- 统一 ACL 平台

### 3.2 权限模型
系统权限分两层：

#### 3.2.1 全局角色
由 `t_role` + `t_user_role` 管理，代码中实际使用的全局角色主要包括：
- `ADMIN`
- `CLUB_ADMIN`
- 普通登录用户（前端通常视作学生用户）

#### 3.2.2 社团内部角色
由 `t_member.role_code` 表示，实际代码中使用：
- `PRESIDENT`
- `MANAGER`
- `MEMBER`

`PermissionService` 负责校验：
- 是否系统管理员
- 是否某社团管理员
- 社团是否处于可操作状态

### 3.3 异步消息设计
项目实际使用 `RabbitMQ` 处理通知类异步任务。

当前已实现的主要消息场景：
- 活动报名成功通知
- 通用通知投递
- 社团公告广播
- 招新审核结果通知
- 资源申请审批通知

通知消费者集中在 `community-notice` 模块中监听并落库。

### 3.4 文件与邮件设计
- 文件上传由 `community-user` 的文件接口接收，并通过 `community-core` 中的 `OssTemplate` 上传到阿里云 OSS。
- 邮件能力由 `Spring Mail` 提供，主要用于发送验证码与密码重置场景。

### 3.5 监控与实时能力
- `Micrometer` 指标由主应用暴露给 `Prometheus`。
- 已埋点指标包括登录成功 / 失败、签到次数、资源申请次数等。
- `WebSocket + STOMP` 用于管理端实时看板。

### 3.6 AI 能力设计
`agent` 服务独立运行，提供以下接口：
- `/chat`：社团问答
- `/recommend`：社团推荐
- `/sync`：知识同步
- `/health`：健康检查

Java 端通过 `RestTemplate` 调用该服务。

## 4. 核心业务流程

### 4.1 登录流程
```text
用户登录
-> AuthController 校验用户名密码
-> 生成 access token / refresh token
-> 写入 Cookie
-> refresh token 写入 Redis
-> 前端后续请求自动携带 Cookie
```

### 4.2 招新流程
```text
社团创建批次
-> 配置表单字段
-> 学生提交报名
-> 干部初审
-> 终审
-> 审核结果通知
-> 通过后创建成员记录
```

### 4.3 活动流程
```text
创建活动
-> 学生报名
-> 活动签到
-> 导出签到数据
-> 统计展示
```

### 4.4 通知流程
```text
业务模块发消息到 RabbitMQ
-> notice 模块监听队列
-> 写入站内通知表
-> 前端轮询 / 查询未读数
```

### 4.5 推荐流程
```text
前端请求推荐社团
-> club 模块调用 Python 推荐服务
-> 返回推荐 club id 列表
-> Java 侧查询社团详情并返回前端
```
