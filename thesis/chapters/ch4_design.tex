\chapter{系统设计}

\section{总体架构设计}

\subsection{架构设计原则}

系统架构设计遵循以下核心原则：

\begin{enumerate}
  \item \textbf{模块化原则}：按业务领域划分模块，每个模块职责单一，降低耦合度；
  \item \textbf{分层原则}：采用经典的三层架构（表示层、业务逻辑层、数据访问层），层次清晰；
  \item \textbf{可扩展性原则}：预留扩展点，支持后续功能增加和架构演进；
  \item \textbf{高内聚低耦合原则}：模块内部高度内聚，模块间通过接口交互；
  \item \textbf{安全性原则}：认证授权统一管理，敏感数据加密存储和传输。
\end{enumerate}

\subsection{模块化单体架构}

系统采用“模块化单体”（Modular Monolith）架构。各业务模块在代码层面保持清晰边界，在部署层面仍统一打包为单一应用运行。这种做法适合当前项目的业务复杂度和团队规模。

\subsubsection{模块化单体的优势}

相比传统单体架构，模块化单体具有以下优势：

\begin{enumerate}
  \item \textbf{开发调试成本低}：所有模块在同一进程中运行，无需启动多个独立服务，开发调试更便捷；
  \item \textbf{事务处理简单}：跨模块操作可以直接使用本地事务（ACID），无需分布式事务协调；
  \item \textbf{部署运维简单}：仅需管理单一应用实例，降低了运维复杂度和资源消耗；
  \item \textbf{性能开销小}：模块间调用是进程内方法调用，无网络开销，性能更优；
  \item \textbf{支持渐进式演进}：通过明确的模块边界，后续可以根据需要将特定模块拆分为独立的微服务。
\end{enumerate}

对本课题而言，模块化单体比微服务更容易控制开发、部署和运维复杂度，也更符合当前阶段的实现需求。

各模块的职责说明：

\begin{itemize}
  \item \textbf{community-core}：核心模块，定义所有 JPA 实体类、Repository 接口、统一返回结构、JWT 工具类、OSS 服务、邮件服务等通用能力。该模块被所有业务模块依赖。

  \item \textbf{community-gateway}：网关模块，作为应用启动入口，包含 Spring Boot 主类、Spring Security 配置、JWT 过滤器、全局异常处理器、WebSocket 配置、Dashboard 统计接口等。

  \item \textbf{community-user}：用户模块，负责用户注册、登录、个人信息管理、密码修改、权限校验服务等。

  \item \textbf{community-club}：社团模块，负责社团的创建、审批、查询、推荐、成员管理、解散流程、资源申请、财务管理、AI 聊天入口等。

  \item \textbf{community-activity}：活动模块，负责活动的创建、查询、报名、签到、签到记录导出等。

  \item \textbf{community-recruit}：招新模块，负责招新批次管理、动态表单字段配置、报名申请、初审终审流程、报名结果导出等。

  \item \textbf{community-notice}：通知模块，负责公告的发布与查询、站内通知的生成与推送、RabbitMQ 消息消费等。

  \item \textbf{community-admin}：管理模块，负责系统管理员的审批功能、审计日志查询、统计数据接口等。
\end{itemize}

模块间的依赖关系遵循"单向依赖"原则：业务模块只依赖 core 模块，业务模块之间不直接依赖，通过消息队列或 API 调用实现跨模块通信。

\subsection{部署与运行拓扑}

系统采用容器化部署方案，所有服务通过 Docker 容器运行，并通过 Docker Compose 进行编排。部署拓扑如图~\ref{fig:deploy} 所示。

\subsubsection{前端层}

前端采用 Vue 3 单页应用，通过 Nginx 提供静态文件服务。用户通过浏览器访问前端页面，前端通过 Nginx 反向代理将 API 请求转发到后端服务。这种架构实现了前后端分离，前端可以独立部署和扩展。

\subsubsection{应用层}

应用层包括两个核心服务：

\begin{enumerate}
  \item \textbf{Spring Boot 应用}：运行在 8080 端口，提供所有业务 API 接口，处理用户请求、业务逻辑、数据持久化等；
  \item \textbf{FastAPI AI 服务}：运行在 8000 端口，独立于主应用部署，提供知识问答和社团推荐功能。
\end{enumerate}

两个服务通过 HTTP REST API 进行通信，实现了业务逻辑与 AI 能力的解耦。

\subsubsection{数据层}

数据层包括多种数据存储和中间件：

\begin{itemize}
  \item \textbf{MySQL 8}：主数据库，存储用户、社团、活动、招新等核心业务数据；
  \item \textbf{Redis 7}：缓存和会话存储，用来 JWT 令牌管理、登录限流等；
  \item \textbf{RabbitMQ 3.12}：消息队列，实现异步通知分发；
  \item \textbf{Aliyun OSS}：对象存储服务，存储用户头像、活动封面等文件；
  \item \textbf{Chroma DB}：向量数据库，存储社团知识库的向量表示，支持语义检索。
\end{itemize}

\subsubsection{监控层}

监控层包括 Prometheus 和 Grafana：

\begin{itemize}
  \item \textbf{Prometheus}：定时抓取 Spring Boot 应用暴露的 \texttt{/actuator/prometheus} 指标端点，收集系统运行指标；
  \item \textbf{Grafana}：连接 Prometheus 数据源，提供可视化监控面板，展示系统性能和业务指标。
\end{itemize}

\section{数据模型设计}

\subsection{数据库设计原则}

系统数据库设计遵循以下原则：

\begin{enumerate}
  \item \textbf{规范化原则}：数据库设计遵循第三范式（3NF），减少数据冗余，保证数据一致性；
  \item \textbf{性能优化原则}：在关键查询字段上建立索引，提升查询性能；
  \item \textbf{扩展性原则}：预留扩展字段，支持后续功能增加；
  \item \textbf{完整性原则}：通过外键约束、唯一约束、非空约束等保证数据完整性；
  \item \textbf{审计原则}：关键业务表包含创建时间、更新时间、创建人等审计字段。
\end{enumerate}

\subsection{核心实体关系}

当前版本的 \texttt{schema.sql} 共定义 21 张数据表，其中 20 张承担业务与支撑建模，另有 1 张社团标签辅助表（\texttt{t\_club\_tag}）。除用户、社团、活动、招新、公告通知、资源、财务与审计等主链路外，当前实现还补充了 \texttt{t\_user\_role}（用户-角色关联）、\texttt{t\_member\_point\_record}（成员积分流水）与 \texttt{t\_prohibited\_word}（公告违禁词）等支撑表，用来反映授权、成员激励与内容治理等机制。主要实体可归纳如下：

\begin{itemize}
  \item \textbf{用户与授权}：\texttt{t\_user}（用户表）、\texttt{t\_role}（角色表）、\texttt{t\_user\_role}（用户角色关联表）
  \item \textbf{社团与成员}：\texttt{t\_club}（社团表）、\texttt{t\_club\_tag}（社团标签表）、\texttt{t\_member}（成员表）、\texttt{t\_member\_point\_record}（成员积分流水表）
  \item \textbf{活动管理}：\texttt{t\_activity}（活动表）、\texttt{t\_activity\_signup}（活动报名表）、\texttt{t\_activity\_attendance}（活动签到表）
  \item \textbf{招新管理}：\texttt{t\_recruit\_batch}（招新批次表）、\texttt{t\_recruit\_form\_field}（表单字段表）、\texttt{t\_recruit\_application}（招新申请表）
  \item \textbf{公告、通知与内容治理}：\texttt{t\_notice}（公告表）、\texttt{t\_notice\_read}（公告已读表）、\texttt{t\_notification}（站内通知表）、\texttt{t\_prohibited\_word}（违禁词表）
  \item \textbf{资源与财务管理}：\texttt{t\_resource}（资源定义表）、\texttt{t\_resource\_application}（资源申请表）、\texttt{t\_club\_finance}（财务流水表）
  \item \textbf{审计管理}：\texttt{t\_audit\_log}（审计日志表）
\end{itemize}

图~\ref{fig:er} 仅展示最主要的业务实体与关键关联关系；成员积分流水、违禁词治理等支撑表不在图中逐一展开，但均已在当前 schema 中定义。

实体间的关系遵循以下设计：

\begin{itemize}
  \item 用户与角色是多对多关系，通过中间表 \texttt{t\_user\_role} 关联；
  \item 用户与社团是多对多关系，通过成员表 \texttt{t\_member} 关联，成员表记录用户在社团中的岗位角色；
  \item 社团与标签、成员积分流水、活动、招新批次、公告、资源申请和财务流水均是一对多关系；
  \item 活动与报名、签到是一对多关系；
  \item 招新批次与表单字段、招新申请是一对多关系；
  \item 公告与用户阅读状态通过 \texttt{t\_notice\_read} 形成多对多记录。
\end{itemize}

\subsection{成员积分、待办中心与运营看板交互约定}

除主业务链路外，当前版本还实现了若干面向运营辅助的交互能力，其设计目标不是改变社团创建、招新、活动、审批等核心流程，而是在既有数据之上补充成员激励、待办聚合和运行态观察能力。

成员积分采用“社团内独立核算”的设计。数据上以 \texttt{t\_member.points} 记录成员在某一社团中的当前积分，以 \texttt{t\_member\_point\_record} 记录增减流水、来源类型、来源业务单据和操作人，从而形成“余额 + 流水”双层结构。活动表额外维护 \texttt{reward\_points}、\texttt{need\_attendance}、\texttt{settlement\_status} 与 \texttt{settled\_at} 等字段，用来描述活动奖励额度、结算口径与结算状态。该设计明确约束了积分不跨社团累计，也避免将本应依附成员关系的激励机制误建模为平台统一钱包。

统一待办中心采用“后端聚合、前端渲染”的方式。管理端与社团管理员端统一调用 \texttt{/api/dashboard/todos}，由后端基于当前登录用户角色汇总社团创建审核、解散审批、资源审批、财务审批、招新初审与终审等待办分组，并为每一分组返回待处理数量、代表性条目和跳转路径。这样可以将待办口径收敛到服务端，避免多个前端页面各自拼装统计逻辑而产生不一致。

实时运营看板主要面向管理侧使用。其基础统计由 \texttt{/api/dashboard/stats} 提供，包括活跃社团数、当日签到数、待审资源数和累计报名数；系统级统计由 \texttt{/api/stats/system} 提供，包括社团总量、用户总量、活动总量、状态分布和近七日增长数据；社团活跃排行则基于按社团统计接口进一步组合。该设计强调的是业务运行态可见性，而不是基础设施层面的主机监控。

\section{AI 服务设计}

\subsection{问答链路}

问答模块由 Java 后端 \texttt{/api/club/chat} 转发到 Python \texttt{/chat}。请求里会带 \texttt{sessionId} 和用户上下文（如 \texttt{role\_codes}、\texttt{managed\_club\_ids}）。Python 侧不是黑盒 Agent，而是可控的组件化链路：先按规则判断是否需要调用工具，公告、活动、招新、资源、财务这类问题优先查实时数据；再把知识库片段和近期会话上下文一起用来生成回答。若模型调用或检索不可用，就返回带边界说明的降级结果。

\subsection{推荐链路}

推荐模块由 Java 侧调用 Python \texttt{/recommend}。算法把协同过滤和语义相似度合在一起，并支持 \texttt{cf/cb/hybrid} 三种模式切换。用户没有历史行为，或者单侧得分不可用时，会回退到热门社团排序，保证结果能返回。若跨服务调用异常，当前实现会先返回空列表，再由业务侧兜底展示。

\subsection{AI 服务架构设计}

AI 服务与主应用分开部署，原因如下：

\begin{enumerate}
  \item \textbf{服务隔离}：AI 服务单独运行在 8000 端口，与主应用（8080 端口）物理隔离，避免 AI 推理负载拖慢主业务响应；

  \item \textbf{独立服务调用}：主应用通过 HTTP REST 接口调用 AI 服务。当前版本采用同步请求-响应模式，接入现有业务接口更直接，也能保持 AI 链路与主业务链路的进程隔离；

  \item \textbf{降级策略}：当 AI 服务不可用或向量检索失败时，系统会返回错误提示或谨慎回答；推荐模块在冷启动或单侧得分不可用时回退热门社团，跨服务异常时返回空列表并由业务侧兜底展示，尽量不影响核心业务；

  \item \textbf{独立演进}：由于 AI 服务与主应用解耦，后续可以在不改动主要业务模块的前提下调整模型、提示词、检索策略和推荐权重；

  \item \textbf{边界清晰}：问答、推荐和知识库维护都集中在 Python 服务侧，便于单独测试、补测和留档。
\end{enumerate}

\subsection{AI 侧访问控制}

AI 问答链路和业务权限是打通的，目的是避免“登录后可以问到所有内容”的越权问题。具体做法如下：

\begin{enumerate}
  \item \textbf{上下文透传}：Java 在转发 \texttt{/chat} 请求时，会带上 \texttt{authenticated}、\texttt{user\_id}、\texttt{role\_codes}、\texttt{managed\_club\_ids}、\texttt{managed\_club\_names} 等上下文信息；

  \item \textbf{统一访问级别}：Python 侧把工具与知识文档的访问要求统一成 \texttt{public}、\texttt{authenticated}、\texttt{admin}、\texttt{club\_admin} 四类级别；

  \item \textbf{工具与检索双重过滤}：实时工具调用前先做权限判断；向量检索结果再按文档元数据中的 \texttt{visibility}、\texttt{club\_id} 等字段过滤，只保留当前用户能看到的内容；

  \item \textbf{越权响应边界}：当用户触发受限查询时，系统直接返回权限提示，不再拼接后续敏感上下文，避免绕过路由进入生成阶段。
\end{enumerate}

\subsection{知识库维护机制}

AI 问答服务稳不稳，很大程度取决于知识库能不能持续更新。为此，当前版本采用“启动初始化 + 接口增量 + 数据库同步 + 周期重载”的组合机制：

\begin{enumerate}
  \item \textbf{启动初始化}：AI 服务启动时从 \texttt{agent/data/} 目录加载 Markdown 知识文件，并构建本地 Chroma 向量库；

  \item \textbf{接口增量更新}：通过 \texttt{/sync} 接口执行 \texttt{upsert/delete}，支持文档新增、更新和删除，适合小规模人工改动；

  \item \textbf{数据库生成知识文档}：通过 \texttt{sync\_db\_knowledge.py} 从业务库抽取社团、活动、招新、公告、资源等数据生成本地 Markdown 文档，并写入 \texttt{generated\_by=db-sync}、\texttt{visibility} 等元数据；

  \item \textbf{周期同步}：在 Docker Compose 中由 \texttt{rag-sync} 侧车容器周期执行 \texttt{sync\_db\_loop.py}，按配置间隔增量刷新知识文件，并支持过期文档清理（prune）；

  \item \textbf{热重载}：同步任务更新文档后可调用 \texttt{/knowledge/reload} 触发向量库重建，避免每次都重启 AI 服务；

  \item \textbf{文档切分}：文本使用 \texttt{RecursiveCharacterTextSplitter} 切分，当前参数为 \texttt{chunk\_size=1000}、\texttt{chunk\_overlap=200}，用来平衡检索粒度与上下文完整性；

  \item \textbf{向量化}：嵌入层通过本地封装函数创建，默认使用 \texttt{all-MiniLM-L6-v2}；若句向量依赖不可用，则回退为本地哈希向量表示，保证离线环境下也能基本运行；

  \item \textbf{持久化}：向量索引保存在 \texttt{agent/chroma\_db/}，便于本地复现和重复加载。
\end{enumerate}

\section{性能优化设计}

\subsection{数据库查询优化}

系统在数据库层面采用多种优化策略，提升查询性能：

\begin{enumerate}
  \item \textbf{索引优化}：在高频查询字段上建立索引，如社团状态（\texttt{idx\_club\_status}）、活动时间（\texttt{idx\_activity\_start\_time}）、审计日志创建时间（\texttt{idx\_audit\_created\_at}）等；

  \item \textbf{复合索引}：对于多字段联合查询，建立复合索引，如活动报名表的 \texttt{(activity\_id, user\_id)} 复合唯一索引，既保证唯一性又加速查询；

  \item \textbf{分页查询}：所有列表查询接口均采用分页机制，默认每页 20 条记录，避免一次性加载大量数据；

  \item \textbf{延迟加载}：JPA 实体关联关系默认使用 \texttt{LAZY} 加载策略，仅在实际访问关联对象时才触发查询，减少不必要的 JOIN 操作；

  \item \textbf{查询优化}：避免 N+1 查询问题，使用 \texttt{JOIN FETCH} 或 \texttt{@EntityGraph} 一次性加载关联数据。
\end{enumerate}



\subsection{缓存策略设计}

系统使用 Redis 作为分布式缓存，缓存策略如下：

\begin{enumerate}
  \item \textbf{会话缓存}：用户登录后的 JWT 令牌存储在 Redis 中，键名为 \texttt{auth:token:\{jwt\}}，过期时间与令牌一致（1 小时），支持主动失效；

  \item \textbf{限流计数}：登录失败次数、聊天请求频率等限流数据存储在 Redis 中，利用 Redis 的原子递增操作和过期机制实现滑动窗口限流；

  \item \textbf{热点数据缓存}：社团列表、活动列表等高频查询数据可以缓存在 Redis 中，设置合理的过期时间（如 5 分钟），减少数据库压力；

  \item \textbf{缓存更新策略}：采用"先更新数据库，再删除缓存"的策略，保证数据一致性，下次查询时自动重建缓存；

  \item \textbf{缓存穿透防护}：对于不存在的数据，缓存空值（如空列表），设置较短的过期时间（如 1 分钟），避免恶意查询击穿缓存。
\end{enumerate}

\subsection{并发控制设计}

系统在高并发场景下采用多种并发控制机制，保证数据一致性：

\begin{enumerate}
  \item \textbf{悲观锁}：在招新终审、活动报名、资源审批、财务审批等关键业务场景使用数据库悲观锁（\texttt{SELECT ... FOR UPDATE}），确保同一时刻只有一个事务可以修改数据；

  \item \textbf{唯一约束}：在数据库层面建立唯一约束，如活动报名表的 \texttt{(activity\_id, user\_id)} 唯一键，从根本上防止重复数据；

  \item \textbf{重复写入防护}：关键写接口以“避免重复写入和状态错乱”为目标，主要依赖唯一约束、业务状态校验与悲观锁实现；在当前版本中，重复报名、重复签到、重复审批等请求通常返回业务错误，而不是一律以“幂等成功”方式吞掉重复调用；

  \item \textbf{分布式锁}：对于跨实例的并发控制场景（如定时任务），可以使用 Redis 分布式锁，保证同一时刻只有一个实例执行任务；

  \item \textbf{乐观锁}：对于冲突概率较低的场景，可以使用版本号机制实现乐观锁，减少锁等待时间。
\end{enumerate}


\section{异常处理与日志设计}

\subsection{统一异常处理机制}

系统通过 Spring 的全局异常处理器统一处理各类异常，保证错误响应的一致性：

\begin{enumerate}
  \item \textbf{业务异常}：自定义 \texttt{BusinessException} 类，包含错误码和错误消息，用来表示可预期的业务错误（如"名额已满"、"权限不足"等）；

  \item \textbf{参数校验异常}：使用 JSR-303 Bean Validation 进行参数校验，校验失败时抛出 \texttt{MethodArgumentNotValidException}，全局处理器提取校验错误信息并返回；

  \item \textbf{认证授权异常}：Spring Security 抛出的 \texttt{AuthenticationException} 和 \texttt{AccessDeniedException} 统一转换为 401 和 403 响应；

  \item \textbf{系统异常}：未预期的系统异常（如 \texttt{NullPointerException}、\texttt{SQLException}）统一返回 500 错误，隐藏内部实现细节，避免信息泄露；

  \item \textbf{异常日志}：所有异常均记录完整堆栈信息到日志文件，便于问题排查和监控告警。
\end{enumerate}

\subsection{日志分级策略}

系统采用 Logback 作为日志框架，日志分级策略如下：

\begin{enumerate}
  \item \textbf{ERROR 级别}：记录系统错误和异常，如数据库连接失败、外部服务调用失败、未捕获的运行时异常等，需要立即处理；

  \item \textbf{WARN 级别}：记录潜在问题和警告信息，如缓存未命中、降级策略触发、配置项缺失使用默认值等，需要关注但不影响核心功能；

  \item \textbf{INFO 级别}：记录关键业务操作，如用户登录、社团创建、活动报名、审批操作等，用来业务审计和问题追溯；

  \item \textbf{DEBUG 级别}：记录详细的调试信息，如 SQL 语句、方法参数、中间结果等，仅在开发和测试环境启用；

  \item \textbf{TRACE 级别}：记录最详细的跟踪信息，如框架内部调用链路，通常不启用，仅在深度排查问题时临时开启。
\end{enumerate}


\subsection{日志文件管理}

系统日志文件按日期滚动，保留策略如下：

\begin{enumerate}
  \item \textbf{应用日志}：\texttt{application.log}，记录应用运行日志，每天滚动一次，保留最近 30 天；

  \item \textbf{错误日志}：\texttt{error.log}，仅记录 ERROR 级别日志，每天滚动一次，保留最近 90 天；

  \item \textbf{访问日志}：\texttt{access.log}，记录所有 HTTP 请求，每天滚动一次，保留最近 7 天；

  \item \textbf{审计日志}：审计日志存储在数据库中，不设置自动清理策略，长期保留用来合规审计；

  \item \textbf{日志压缩}：滚动后的日志文件自动压缩为 gzip 格式，节省存储空间。
\end{enumerate}

\section{监控与告警设计}

\subsection{指标采集设计}

系统通过 Spring Boot Actuator 和 Micrometer 暴露监控指标，Prometheus 定时抓取：

\begin{enumerate}
  \item \textbf{JVM 指标}：堆内存使用率、GC 次数和耗时、线程数、类加载数等，监控应用运行状态；

  \item \textbf{HTTP 指标}：请求总数、响应时间分布（P50/P95/P99）、错误率等，监控接口性能；

  \item \textbf{数据库指标}：连接池使用率、SQL 执行时间、慢查询数量等，监控数据库性能；

  \item \textbf{缓存指标}：Redis 命中率、连接数、内存使用率等，监控缓存效果；

  \item \textbf{业务指标}：登录成功/失败次数、活跃社团数、待审批数量等，监控业务运行情况。
\end{enumerate}


\subsection{告警规则设计}

系统在 Prometheus 中配置告警规则，当指标异常时触发告警：

\begin{enumerate}
  \item \textbf{服务可用性告警}：应用实例下线超过 1 分钟，触发紧急告警；

  \item \textbf{错误率告警}：5 分钟内 HTTP 5xx 错误率超过 5\%，触发警告告警；

  \item \textbf{响应时间告警}：接口 P95 响应时间超过 2 秒，触发警告告警；

  \item \textbf{资源使用告警}：JVM 堆内存使用率超过 85\%，触发警告告警；超过 95\% 触发紧急告警；

  \item \textbf{数据库连接告警}：数据库连接池使用率超过 80\%，触发警告告警。
\end{enumerate}

\subsection{可视化监控面板}

系统使用 Grafana 构建可视化监控面板，主要包括：

\begin{enumerate}
  \item \textbf{系统概览面板}：展示应用实例状态、请求 QPS、错误率、响应时间等核心指标；

  \item \textbf{JVM 监控面板}：展示堆内存使用趋势、GC 频率、线程数变化等 JVM 运行状态；

  \item \textbf{数据库监控面板}：展示连接池使用率、SQL 执行时间分布、慢查询列表等数据库性能指标；

  \item \textbf{业务监控面板}：展示用户活跃度、社团数量趋势、活动报名统计等业务运营数据；

  \item \textbf{告警历史面板}：展示历史告警记录、告警频率统计、告警处理时长等告警管理数据。
\end{enumerate}
