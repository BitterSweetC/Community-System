\chapter{绪论}

\section{研究背景与意义}

近年来，随着高等教育规模的持续扩大，高校学生社团数量与成员人数呈现出快速增长的态势。社团作为高校第二课堂的重要组成部分，在培养学生综合素质、丰富校园文化生活方面发挥着不可替代的作用。然而，传统的社团管理模式普遍依赖纸质表单、电话沟通与人工协调，存在以下突出问题：

\begin{enumerate}
  \item \textbf{信息孤岛严重}：各社团数据分散存储，缺乏统一的信息平台，学校管理部门难以实时掌握社团运营状况；
  \item \textbf{流程繁琐低效}：社团注册、活动审批、招新报名等流程均需线下办理，耗时耗力，且容易出现信息丢失；
  \item \textbf{数据难以追溯}：活动签到、财务收支等记录缺乏电子化存档，审计与统计工作困难；
  \item \textbf{通知触达率低}：依赖微信群、公告栏等非正式渠道发布通知，信息传递不及时、不准确。
\end{enumerate}

信息化建设是解决上述问题的重要路径。构建一套功能完善、安全可靠的高校社团管理系统，有助于提升社团管理效率，降低行政协调成本，并为学生提供更便捷的参与渠道，促进校园文化的持续发展。因此，围绕高校社团管理场景开展系统设计与实现研究，具有较强的现实意义与应用价值。

\section{国内外研究现状}

\subsection{国内研究现状}

从国内高校公开流程材料、已有系统形态与工程实现资料看，教务管理、图书馆管理、学生事务等核心业务已形成较成熟的信息化基础，但围绕社团治理、第二课堂活动与学生自治组织运行的专项系统建设仍相对分散。为把握这一细分场景所处的更广泛高等教育数字化背景，相邻综述研究指出，高校数字化建设已从单一教学工具应用扩展到组织战略、流程再造、数据治理以及学生服务整合等层面\cite{fernandez_he_dt_2023,mukul_education4_2023,mabotha_he_dt_2026}。与此同时，学生与教师视角研究显示，高校实际数字化实践仍常表现为平台分散、基础设施与数字素养不均衡，以及供给方式与用户期待之间存在落差\cite{aljanazrah_dt_crisis_2022,potocan_he_students_2025}。需要说明的是，就高校社团管理这一细分场景而言，本文能够获取的材料同时包括公开可见的系统形态、工程实现资料与通用技术研究文献，本节更侧重为后续工程设计建立问题背景，而非构成穷尽式教育信息化综述。

从公开可见的系统形态与工程实现路线看，高校社团管理相关方案大致可分为三类：第一类是基于通用 OA 系统的简单扩展，能够覆盖审批流与通知公告等基础流程，但对社团全生命周期管理的适配不足；第二类是高校自主开发的轻量级平台，此类方案多继承早期 JavaEE 或 JSP/Servlet 技术路径，功能相对完整，但在模块边界、可维护性与交互体验方面存在局限；第三类是近年来兴起的 SaaS 化社团管理平台，部署便捷，但在数据主权、校内业务定制与本地化适配方面相对受限。这些材料能够帮助识别常见功能边界与实现取舍，但往往缺少统一的公开评测口径。

随着 Spring Boot、Vue 等现代技术栈的普及，相关系统建设逐渐由“功能上线”转向“架构演进”。一类方案倾向于采用微服务架构以提升模块独立性与扩展能力\cite{microservices2015}；另一类方案则强调在中等系统复杂度下以模块化单体降低部署与运维成本\cite{microservices_patterns2018}。总体来看，现有公开成果更多聚焦业务流程电子化与架构拆分，对认证安全、实时协同以及 AI 辅助能力的协同设计讨论仍然不足，且不同资料之间的证据强度并不一致。

\subsection{国外研究现状}

国外高校在学生事务管理信息化方面起步较早，相关研究与实践更强调平台整合、服务化架构以及跨系统协同\cite{microservices2015}。近年来，关于高等教育数字化转型的综述更明确地将其界定为涉及战略、流程、数据与用户体验的组织性变革，而非单纯的技术部署\cite{fernandez_he_dt_2023,mabotha_he_dt_2026}。Education 4.0 相关系统综述进一步指出，个性化、灵活性、实时连接与 AI 支撑已成为数字教育环境的重要特征\cite{mukul_education4_2023}。在工程实现上，商业化 SIS 或校园服务平台通常具有较完善的流程规范与治理经验，但也面临部署成本较高、场景细粒度不足以及对本地组织结构适配有限等问题。需要指出的是，可直接对应“高校社团管理系统”的专门研究并不集中，因此本文更多借助学生事务平台、知识服务与推荐系统等相邻方向的成果进行参照。教育推荐系统的系统综述表明，现有研究主要围绕学习资源、课程路径与学习者支持展开，冷启动、数据稀疏性与评价口径仍是高频问题\cite{urdaneta_education_rs_2021,deschenes_rs_2020}。近期针对教育场景的 RAG 聊天机器人综述进一步指出，该方向虽增长迅速，但应用重点仍集中于课程答疑、教学支持和学习辅助，对非课堂学生事务治理的覆盖仍然有限\cite{swacha_rag_education_2025}。

\subsection{现有系统的不足}

综合公开系统形态、工程资料与相关技术研究，现有系统主要存在以下不足：
\begin{enumerate}
  \item 缺乏完整的社团全生命周期管理（从申请、审批到解散）；
  \item 实时交互能力弱，缺乏签到等关键场景的实时广播能力，通知侧通常仅支持轮询；
  \item AI 智能服务集成度低，缺乏个性化推荐与智能问答功能；
  \item 安全机制不完善，缺乏细粒度的 RBAC 权限控制与审计日志\cite{rbac_model}。
\end{enumerate}

\section{研究内容与目标}

\noindent 本文定位为面向高校社团管理场景的系统设计与实现研究，在论文类型上属于系统设计与实现型本科毕业论文。研究重点在于提出一套兼顾部署复杂度、功能完整性与后续演进能力的工程方案，并通过阶段性测试对系统的核心业务性能、认证链路、实时交互与 AI 辅助能力进行验证。与纯理论研究或严格实证研究不同，本文更强调“方案设计-系统实现-阶段性评估”的闭环。

\subsection{系统功能目标}

本系统旨在实现以下核心功能：
\begin{enumerate}
  \item 用户注册、登录、权限管理及个人信息维护；
  \item 社团创建申请、审批、成员管理及生命周期管理；
  \item 活动发布、报名、签到码生成与核验、数据导出；
  \item 招新批次管理、动态表单配置与多阶段审核；
  \item 站内通知与公告管理（通知异步分发，前端轮询读取）；
  \item 财务收支记录、审批与余额管理；
  \item 场地与设备资源申请及冲突检测；
  \item AI 智能社团推荐与知识库问答服务。
\end{enumerate}

\subsection{技术目标}

\begin{enumerate}
  \item \textbf{高安全性}：基于 JWT 双令牌机制与 RBAC 权限模型构建访问控制，并通过输入校验与 Cookie 策略降低常见攻击风险；
  \item \textbf{高性能}：利用 Redis 缓存与数据库索引优化高频路径，并建立可量化的性能压测基线；
  \item \textbf{高可用}：完善异常处理与降级机制，提升单实例场景下的稳定性与可恢复性；
  \item \textbf{可扩展}：模块化架构设计，各业务模块低耦合，便于后续功能扩展与微服务化演进。
\end{enumerate}

\subsection{研究问题}

围绕上述目标，本文重点回答以下研究问题：
\begin{enumerate}
  \item 在当前原型范围与单节点部署假设下，模块化单体架构能否在保持部署复杂度可控的前提下支撑社团全生命周期业务？
  \item 在当前工程验证口径下，结合 JWT、HttpOnly Cookie 与 Redis 会话校验的认证机制，以及 WebSocket/RabbitMQ 协同通知机制，系统在安全控制与实时交互方面能够达到怎样的阶段性可用水平？
  \item 在当前项目知识库、测试数据与补测条件下，RAG 问答与推荐模块能够呈现怎样的阶段性可用性；哪些结论属于可复验结果，哪些仅为内部观察值？
\end{enumerate}

\subsection{研究范围界定}

本系统面向高校校内使用场景，用户群体包括普通学生、社团成员、社团管理员与系统管理员。系统部署于校内服务器，通过浏览器访问，不涉及移动端原生应用开发。本文需求来源以场景化业务建模、公开流程材料与项目实现约束为主（第三章），并非以大样本问卷或访谈作为主证据。本文的 AI 模块评估以项目内部题集、样例场景、补测脚本与人工核验结果为基础，相关复现入口统一挂载于附录；由于当前仓库中未包含逐题标注文件与推荐样例原始记录，本文不将其界定为公开 benchmark、在线 A/B 实验或大规模用户研究。

\subsection{研究方法与评估思路}

本文采用“需求分析—系统设计—系统实现—阶段性验证”的工程研究路径，主要方法如下：

\begin{enumerate}
  \item \textbf{场景驱动与公开资料辅助的需求分析}：围绕高校社团管理中的创建审批、活动组织、招新、资源与财务申请、通知触达等典型流程，结合公开流程材料与系统形态梳理系统边界、功能需求与非功能需求；
  \item \textbf{面向实现的架构设计}：针对部署复杂度、认证控制、实时交互与后续演进等问题，完成模块化单体架构、数据模型、权限链路与 AI 服务链路设计；
  \item \textbf{原型实现与代码级验证}：基于 Spring Boot、Vue 3、MySQL、Redis、RabbitMQ 与 FastAPI 完成系统原型，并通过单元测试、接口烟测、前端流程验证等方式检查主要功能路径；
  \item \textbf{阶段性工程评估}：通过 JMeter 对核心业务链路建立当前版本的性能基线，并基于项目内部题集、样例场景、人工核验与在线链路补测对 AI 模块开展阶段性可用性观察。
\end{enumerate}

需要说明的是，本文的评估重点在于论证既定方案在当前场景下的工程可行性与实现效果，而非形成可直接外推的普适性算法结论或生产级部署结论。

\subsection{主要工作特点与阶段性发现}

相较现有高校社团管理系统，本文更强调可复用的工程设计取舍与阶段性观察，主要体现在以下几个方面：

\begin{enumerate}
  \item \textbf{模块化单体架构的工程化实践}：针对高校社团管理场景，提出了一种介于传统单体与微服务之间的模块化单体架构方案。通过 Maven 多模块组织、明确的模块边界与依赖管理，在保持单体应用部署简便性的同时，实现了业务模块的高内聚低耦合，为后续向微服务演进预留了清晰路径。该方案在当前单节点原型场景下有利于控制部署与运维复杂度。

  \item \textbf{混合认证机制的工程实现}：本文实现了结合 JWT 双令牌、HttpOnly Cookie 与 Redis 会话校验的认证方案。该方案既保留了 JWT 的无状态优势，又通过 Redis 二次校验增强了会话可控性，同时利用 HttpOnly Cookie 降低令牌被脚本窃取的风险，在认证控制与访问性能之间取得了较好的工程平衡。

  \item \textbf{实时与异步协同的通知架构}：针对高校社团管理中“签到需要及时反馈”与“通知可以异步送达”的差异化需求，设计了分层通知架构：关键实时场景（活动签到）采用 WebSocket 主动推送，实现页面侧的实时人数更新；非关键通知场景采用 RabbitMQ 异步分发 + 数据库持久化 + 前端轮询读取的组合方案，在保证消息可靠性的同时避免了 WebSocket 连接数过多导致的资源消耗。阶段性压测结果显示，该架构能够支撑当前脚本条件下的核心交互流程。

  \item \textbf{RAG 增强的社团知识问答}：将检索增强生成（RAG）技术应用于高校社团管理场景，构建了基于 LangChain Agent 与 Chroma 向量数据库的知识问答系统。当前版本通过加载项目知识文件并提供手动补充入口维护知识库，结合嵌入模型与本地向量存储实现语义级别的知识检索；同时在特定问题类型上优先调用业务工具查询实时数据，以增强回答的可用性。在项目内部自建 200 题题集的聚合人工核验中，该模块呈现出一定辅助可用性；但仓库目前尚未保留逐题判定表与题集原文，相关结果尚不具备独立复算条件，题集规模、人工标注一致性与公开基线仍有待进一步完善。

  \item \textbf{混合推荐与冷启动兜底策略}：针对高校新生入学时大量新用户涌入的冷启动问题，设计了融合协同过滤与内容推荐的推荐模块。协同过滤侧采用 TruncatedSVD 挖掘用户-社团隐含关系，内容侧基于社团文本向量与用户兴趣标签计算语义相似度；在有历史行为时进行混合排序，在无历史行为时通过热门社团回退保证结果可返回。该设计首先保证了新用户场景下的结果可返回性，也为后续开展更严格的推荐效果评估提供了实现基础。
\end{enumerate}

\section{论文结构安排}

本文共分七章，各章内容安排如下：

第一章为绪论，介绍研究背景、国内外现状、研究目标与论文结构。

第二章介绍系统所采用的相关技术，包括后端技术栈、前端技术栈、AI 服务及基础设施。

第三章进行系统需求分析，包括功能性需求、非功能性需求及用例分析。

第四章阐述系统设计，涵盖总体架构、数据库设计、安全架构、接口设计及 AI 服务设计。

第五章描述系统的具体实现，包括后端核心模块、前端页面及 AI 服务的代码实现。

第六章介绍系统测试，包括单元测试、接口测试、安全测试与性能测试。

第七章对全文进行总结，并展望未来的改进方向。
