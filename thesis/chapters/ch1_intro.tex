\chapter{绪论}

\section{研究背景与意义}

近年来，随着高等教育规模的持续扩大，高校学生社团数量与成员人数呈现出快速增长的态势。社团作为高校第二课堂的重要组成部分，在培养学生综合素质、丰富校园文化生活方面发挥着不可替代的作用。然而，传统的社团管理模式普遍依赖纸质表单、电话沟通与人工协调，主要存在以下几方面问题：

\begin{enumerate}
  \item \textbf{信息孤岛严重}：各社团数据分散存储，缺乏统一的信息平台，学校管理部门难以实时掌握社团运营状况；
  \item \textbf{流程繁琐低效}：社团注册、活动审批、招新报名等流程均需线下办理，耗时耗力，且容易出现信息丢失；
  \item \textbf{数据难以追溯}：活动签到、财务收支等记录缺乏电子化存档，审计与统计工作困难；
  \item \textbf{通知触达率低}：依赖微信群、公告栏等非正式渠道发布通知，信息传递不及时、不准确。
\end{enumerate}

这些问题不仅增加了学校管理部门与社团负责人的沟通成本，也影响了学生获取信息和参与活动的便利性。随着高校治理逐步向数字化、平台化发展，围绕社团场景构建一套覆盖申请、审批、活动、通知、资源与财务等环节的管理系统，已经具有明显的现实需求。因此，围绕高校社团管理场景开展系统设计与实现研究，不仅具有较强的应用价值，也能够为中等复杂度校园业务系统的架构选择与工程落地提供参考。

\section{国内外研究现状}

\subsection{国内研究现状}

从国内高校公开流程材料、已有系统形态与工程实现资料看，教务管理、图书馆管理、学生事务等核心业务已形成较成熟的信息化基础，但围绕社团治理、第二课堂活动与学生自治组织运行的专项系统建设仍相对分散。为把握这一细分场景所处的更广泛高等教育数字化背景，相邻综述研究指出，高校数字化建设已从单一教学工具应用扩展到组织战略、流程再造、数据治理以及学生服务整合等层面\cite{fernandez_he_dt_2023,mukul_education4_2023,mabotha_he_dt_2026}。与此同时，学生与教师视角研究显示，高校实际数字化实践仍常表现为平台分散、基础设施与数字素养不均衡，以及供给方式与用户期待之间存在落差\cite{aljanazrah_dt_crisis_2022,potocan_he_students_2025}。就高校社团管理这一细分场景而言，当前能够获取的材料同时包括公开可见的系统形态、工程实现资料与通用技术研究文献，因此这一节更侧重为后续工程设计建立问题背景，而不是试图构成一篇穷尽式的教育信息化综述。

从公开可见的系统形态与工程实现路线看，高校社团管理相关方案大致可分为三类：第一类是基于通用 OA 系统的简单扩展，能够覆盖审批流与通知公告等基础流程，但对社团全生命周期管理的适配不足；第二类是高校自主开发的轻量级平台，此类方案多继承早期 JavaEE 或 JSP/Servlet 技术路径，功能相对完整，但在模块边界、可维护性与交互体验方面存在局限；第三类是近年来兴起的 SaaS 化社团管理平台，部署便捷，但在数据主权、校内业务定制与本地化适配方面相对受限。这些材料能够帮助识别常见功能边界与实现取舍，但往往缺少统一的公开评测口径。

随着 Spring Boot、Vue 等现代技术栈的普及，相关系统建设逐渐由“功能上线”转向“架构演进”。一类方案倾向于采用微服务架构以提升模块独立性与扩展能力\cite{microservices2015}；另一类方案则强调在中等系统复杂度下以模块化单体降低部署与运维成本\cite{microservices_patterns2018}。总体来看，现有公开成果更多聚焦业务流程电子化与架构拆分，对认证安全、实时协同以及 AI 辅助能力的协同设计讨论仍然不足，且不同资料之间的证据强度并不一致。

\subsection{国外研究现状}

国外高校在学生事务管理信息化方面起步较早，相关研究与实践更强调平台整合、服务化架构以及跨系统协同\cite{microservices2015}。近年来，关于高等教育数字化转型的综述更明确地将其界定为涉及战略、流程、数据与用户体验的组织性变革，而非单纯的技术部署\cite{fernandez_he_dt_2023,mabotha_he_dt_2026}。Education 4.0 相关系统综述进一步指出，个性化、灵活性、实时连接与 AI 支撑已逐渐成为数字教育环境中的重要特征\cite{mukul_education4_2023}。在工程实现上，商业化 SIS 或校园服务平台通常具有较完善的流程规范与治理经验，但也面临部署成本较高、场景细粒度不足以及对本地组织结构适配有限等问题。就现有公开文献而言，可直接对应“高校社团管理系统”的专门研究并不集中，因此这篇论文更多借助学生事务平台、知识服务与推荐系统等相邻方向的成果进行参照。教育推荐系统的系统综述表明，现有研究主要围绕学习资源、课程路径与学习者支持展开，冷启动、数据稀疏性与评价口径仍是高频问题\cite{urdaneta_education_rs_2021,deschenes_rs_2020}。近期针对教育场景的 RAG 聊天机器人综述进一步指出，该方向虽增长迅速，但应用重点仍集中于课程答疑、教学支持和学习辅助，对非课堂学生事务治理的覆盖还比较有限\cite{swacha_rag_education_2025}。

\subsection{现有系统的不足}

综合公开系统形态、工程资料与相关技术研究，现有系统主要存在以下不足：
\begin{enumerate}
  \item 缺乏完整的社团全生命周期管理（从申请、审批到解散）；
  \item 实时交互能力弱，缺乏签到等关键场景的实时广播能力，通知侧通常仅支持轮询；
  \item AI 智能服务集成度低，缺乏个性化推荐与智能问答功能；
  \item 安全机制不完善，缺乏细粒度的 RBAC 权限控制与审计日志\cite{rbac_model}。
\end{enumerate}

\section{研究内容与目标}

\noindent 这篇论文定位为面向高校社团管理场景的系统设计与实现研究，在论文类型上属于系统设计与实现型本科毕业论文。研究重点在于提出一套兼顾部署复杂度、功能完整性与后续演进能力的工程方案，并通过测试对系统的核心业务性能、认证链路、实时交互与 AI 辅助能力进行验证。与纯理论研究或严格实证研究不同，这篇论文更强调“方案设计-系统实现-测试验证”的完整闭环。

\subsection{系统功能目标}

本系统要实现以下核心功能：
\begin{enumerate}
  \item 用户注册、登录、权限管理及个人信息维护；
  \item 社团创建申请、审批、成员管理及生命周期管理；
  \item 活动发布、报名、签到码生成与核验、数据导出；
  \item 招新批次管理、动态表单配置与多阶段审核；
  \item 站内通知与公告管理（通知异步分发，前端轮询读取）；
  \item 财务收支记录、审批与余额管理；
  \item 场地与设备资源申请及冲突检测；
  \item AI 智能社团推荐与知识库问答服务。
\end{enumerate}

除此之外，系统还补充了社团范围内的成员积分档案、按角色聚合的统一待办中心与管理端实时运营看板（实时大屏）等辅助能力，用来支撑成员激励、审核聚合与运行态观察。

\subsection{技术目标}

\begin{enumerate}
  \item \textbf{高安全性}：基于 JWT 双令牌机制与 RBAC 权限模型构建访问控制，并通过输入校验与 Cookie 策略降低常见攻击风险；
  \item \textbf{高性能}：利用 Redis 缓存与数据库索引优化高频路径，并建立可量化的性能压测基线；
  \item \textbf{高可用}：完善异常处理与降级机制，提升单实例场景下的稳定性与可恢复性；
  \item \textbf{可扩展}：模块化架构设计，各业务模块低耦合，便于后续功能扩展与微服务化演进。
\end{enumerate}

\subsection{研究问题}

围绕上述目标，这篇论文重点回答以下研究问题：
\begin{enumerate}
  \item 在当前原型范围与单节点部署假设下，模块化单体架构能否在保持部署复杂度可控的前提下支撑社团全生命周期业务？
  \item 在当前工程验证口径下，结合 JWT、HttpOnly Cookie 与 Redis 会话校验的认证机制，以及 WebSocket/RabbitMQ 协同通知机制，系统在安全控制与实时交互方面能够达到怎样的可用水平？
  \item 在当前项目知识库、测试数据与补测条件下，RAG 问答与推荐模块能够呈现怎样的实际表现；哪些结论属于可复验结果，哪些仅为内部观察值？
\end{enumerate}

\subsection{研究范围界定}

本系统面向高校校内使用场景，用户群体包括普通学生、社团成员、社团管理员与系统管理员。系统部署于校内服务器，通过浏览器访问，不涉及移动端原生应用开发。这篇论文需求来源以场景化业务建模、公开流程材料与项目实现约束为主（第三章），不是以大样本问卷或访谈作为主证据。这篇论文的 AI 模块评估以项目内部题集、样例场景、补测脚本与人工核验结果为基础，相关复现入口统一挂载于附录；其中，问答部分当前仍未包含逐题标注文件，推荐部分虽已补充模式对比原始记录，但仍缺少相关性标签与在线行为数据，因此这篇论文不将其界定为公开基准测试、在线 A/B 实验或大规模用户研究。

\subsection{研究方法与评估思路}

这篇论文采用“需求分析—系统设计—系统实现—测试验证”的工程研究路径，主要方法如下：

\begin{enumerate}
  \item \textbf{场景驱动与公开资料辅助的需求分析}：围绕高校社团管理中的创建审批、活动组织、招新、资源与财务申请、通知触达等典型流程，结合公开流程材料与系统形态梳理系统边界、功能需求与非功能需求；
  \item \textbf{面向实现的架构设计}：针对部署复杂度、认证控制、实时交互与后续演进等问题，完成模块化单体架构、数据模型、权限链路与 AI 服务链路设计；
  \item \textbf{原型实现与代码级验证}：基于 Spring Boot、Vue 3、MySQL、Redis、RabbitMQ 与 FastAPI 完成系统原型，并通过单元测试、接口冒烟测试、前端流程验证等方式检查主要功能路径；
  \item \textbf{工程验证与效果评估}：通过 JMeter 对核心业务链路建立当前版本的性能基线，并基于项目内部题集、样例场景、人工核验与在线链路补测对 AI 模块开展可用性观察。
\end{enumerate}

这篇论文的评估重点在于说明既定方案在当前场景下是否可实现、可运行，以及实现后的整体效果，而不是直接推出普适性的算法结论或生产级部署结论。

\subsection{主要工作特点与研究发现}

相较现有高校社团管理系统，这篇论文更强调可复用的工程设计取舍与测试结果的相互印证，主要体现在以下几个方面：

\begin{enumerate}
  \item \textbf{模块化单体架构的工程化实践}：针对高校社团管理场景，这篇论文采用了一种介于传统单体与微服务之间的模块化单体架构方案。通过 Maven 多模块组织、明确的模块边界与依赖管理，在保持单体应用部署简便性的同时，尽量实现业务模块的高内聚低耦合，并为后续向微服务演进预留较清晰的路径。就当前单节点原型场景而言，这一方案更有利于控制部署与运维复杂度。

  \item \textbf{混合认证机制的工程实现}：这篇论文实现了结合 JWT 双令牌、HttpOnly Cookie 与 Redis 会话校验的认证方案。该方案既保留了 JWT 的无状态优势，又通过 Redis 二次校验增强了会话可控性，同时利用 HttpOnly Cookie 降低令牌被脚本窃取的风险，在认证控制与访问性能之间取得了较好的工程平衡。

  \item \textbf{实时与异步协同的通知架构}：针对高校社团管理中“签到需要及时反馈”与“通知可以异步送达”的差异化需求，设计了分层通知架构：关键实时场景（活动签到）采用 WebSocket 主动推送，实现页面侧的实时人数更新；非关键通知场景采用 RabbitMQ 异步分发 + 数据库持久化 + 前端轮询读取的组合方案，在兼顾消息可靠性的同时减少 WebSocket 长连接过多带来的资源压力。从当前压测结果看，该架构基本能够支撑既定脚本条件下的核心交互流程。

  \item \textbf{社团边界内的成员激励与运营辅助能力}：针对社团日常运营中的成员激励、审核聚合与运行态观察需求，系统没有设计全站统一积分账户，而是将积分绑定到用户-社团成员关系，并通过积分流水、活动奖励结算与人工调分保持可回溯性；同时，管理端通过统一待办聚合接口和实时运营看板统计接口收敛审核口径与运行指标，减少多页面重复统计带来的管理成本。

  \item \textbf{RAG 增强的社团知识问答}：本系统把检索增强生成（RAG）落到高校社团管理场景里，搭建了“规则路由 + 业务工具 + 检索增强 + 提示词编排”的 LangChain 组件化链路，并用 Chroma 做向量检索。流程上先判断能不能直接查实时业务数据，再用本地知识库补充背景，同时结合用户上下文和文档可见性控制回答范围。知识库维护也不只靠手动补文档，还接入了数据库同步生成和周期重载。项目内部自建 200 题题集的聚合人工核验显示，该模块已经能覆盖一部分常见问答；但仓库里还缺逐题判定表和题集原文，题集规模、标注一致性与公开基线还需要继续补齐。

  \item \textbf{混合推荐与冷启动兜底策略}：针对新生入学阶段新用户集中涌入带来的冷启动问题，这篇论文实现了“协同过滤 + 内容推荐”的融合方案。协同过滤侧用 TruncatedSVD 挖掘用户-社团的隐含关系，内容侧基于社团名称、分类、简介与标签计算语义相似度，再结合行为权重和时间衰减形成用户隐式兴趣画像。用户有历史行为时走混合排序；没有历史行为或单侧得分不可用时回退热门社团，保证推荐结果不断流，也给后续更严格的效果评估留出了实现基础。
\end{enumerate}
